# Quickstart

Goal: an agent running a **governed** query against a data lake in a few minutes.
Pick the path that matches how your agent runs.

## Path A — Hosted MCP (Claude, zero install)

The hosted server lives at `https://api.getwaddling.com/mcp`. Claude connects over
OAuth — nothing to install.

<Steps>
<Step>
### Add the connector

In Claude, add a custom connector pointing at `https://api.getwaddling.com/mcp`.
Claude opens a browser window; sign in and approve. That consent *is* the
credential — no API key to copy.
</Step>
<Step>
### Orient

Ask the agent to call `waddling_whoami` (who am I, what can I access) and
`waddling_list_datalakes` (what lakes can I reach). A brand-new agent may have no
grants yet — that's expected; see step 4.
</Step>
<Step>
### Connect and query

`waddling_connect({ datalake_id })` opens a session and attaches the lake. Then
`waddling_query({ session_id, sql })` — reference tables as `lake.<schema>.<table>`:

```sql
SELECT id, region, amount FROM lake.sales.orders WHERE region = 'EMEA' LIMIT 100
```
</Step>
<Step>
### If you're denied

Access is default-deny. A human grants access in the dashboard under
**Agents → your agent → Access**, or the agent can ask for it — see
[Requesting access](/docs/tutorial-request-access).
</Step>
</Steps>

## Path B — Local MCP (`claude` CLI, scripts, other hosts)

The local server ships on npm and runs over stdio.

<Steps>
<Step>
### Add the server

```sh
claude mcp add waddling npx -- -y @waddling/mcp
```

No key required up front — it starts in onboarding mode.
</Step>
<Step>
### Sign up / link this machine

Ask the agent to call `waddling_signup`. It returns a verify URL and a short code
— open the link, sign in, and the agent's key is saved locally under `~/.waddling/`
as a named **profile**. Poll `waddling_signup_status` until it reports connected.

Already have a key? Import it instead: `waddling_profile_add({ profile, api_key })`.
</Step>
<Step>
### Connect and query

Same as hosted: `waddling_list_datalakes` → `waddling_connect({ datalake_id })` →
`waddling_query({ session_id, sql })`. Sessions refresh transparently — you won't
hit a 15-minute cutoff (see [Workspaces](/docs/workspaces#sessions)).
</Step>
<Step>
### Ask for access when you need it

`waddling_request_access({ datalake_id, grants })` returns a link a human approves;
`waddling_await_access(...)` waits until the grant is live and permanent on your
key. Full walkthrough: [Requesting access](/docs/tutorial-request-access).
</Step>
</Steps>

<Callout type="info" title="Which one?">
Use **hosted** for Claude with the least setup and for shared **memory + topics**.
Use **local** when you want multiple **profiles**, the in-agent **access-request**
flow, or to run inside the `claude` CLI or your own scripts. The tool sets differ —
see [Working through an agent](/docs/agents).
</Callout>

## Create a data lake first (owners)

If no lake exists yet, an owner creates one in the dashboard under **Data lakes →
New**. You bring your own object storage (S3 / R2 / GCS) for the data files;
waddling manages the DuckLake catalog. Details: [Data lakes](/docs/data-lakes).

## What just happened

- The agent authenticated (OAuth or a stored `sk_agent_` key) — it never saw a
  storage credential.
- `connect` provisioned the agent's private **[workspace](/docs/workspaces)** and
  attached the lake into it server-side.
- `query` ran inside that workspace against `lake.*`, and **birdshot** enforced the
  agent's grants — stripping ungranted columns and capping rows.
