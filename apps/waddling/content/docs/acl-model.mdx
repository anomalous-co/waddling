# ACL model

waddling uses **layered enforcement**: each security dimension is enforced at the layer that can actually defend it. No single enforcement layer can be bypassed without hitting another.

## Principals

The unit of policy is the **agent** — a machine principal, not a human. Agents are created in the dashboard or via the admin MCP and hold an API key (`sk_agent_…`). Each agent has a name, a default role, and a status (`active` / `suspended` / `revoked`).

When an agent connects, it authenticates with its API key and receives a **session JWT** (`id` claim = `agent:<agent_id>`, audience = `gw:<endpoint_id>`). This short-lived RS256 token is presented to the gateway as the quack `TOKEN` — the gateway's birdshot extension verifies the signature via JWKS and maps it to the agent's policy.

Humans (org admins and members) are separate from agents. Human sessions are browser-based (Better Auth sessions); agents use API keys + session JWTs.

## Resources

Resources are addressed as `schema → table → column`. Each ACL rule targets a `(schema_name, table_name)` pair with optional `columns[]`. Wildcards (`*`) are supported: `schema_name='*'` matches all schemas; `table_name='*'` matches all tables in a schema.

The DuckLake catalog is implied by the endpoint — one endpoint maps to one DuckLake.

## Verbs and effects

Each rule has a `verb` (`read` or `write`) and an `effect` (`allow` or `deny`). Deny wins on tie. Rules have a `priority` field (lower number = stronger); deny at priority 50 beats allow at priority 100.

**Default is deny**: an agent has no access to any table unless an explicit `allow` rule grants it. Missing rules are not inherited; they are denied.

## Dynamic dimensions — the load-bearing table

This is the heart of the model. Every dimension is enforced at the layer that can actually stop it:

| Dimension | Enforced at | Mechanism |
|-----------|-------------|-----------|
| **table read / write** | **birdshot** (gateway, in-process C++) | Policy compiler emits `birdshot_add_role_grant('agent_<id>', 'schema.table', 'read'/'write')`. Default-deny: ungranted tables are rejected before DuckDB sees the query. |
| **instant revoke** | **birdshot** | `birdshot_revoke('user', 'agent:<id>', reason)` → in-memory denylist. The very next query is denied — no token expiry wait. |
| **TTL / rule expiry** | **birdshot + control plane** | `ttl_seconds` / `expires_at` on a rule → birdshot `expires_at`; the compiler re-pushes a snapshot when rules expire. |
| **session lifetime** | **session JWT `exp`** | RS256 token, default 15 minutes, maximum 1 hour. Gateway re-verifies via JWKS on every new quack connection. |
| **column projection** | **gateway query proxy** | The proxy parses the agent's SELECT, rejects columns not in the `columns[]` allow-list, and rewrites `SELECT *` to the allowed projection before forwarding to DuckDB. Columns are stripped before the query reaches birdshot. |
| **row limit** | **gateway query proxy** | The proxy injects / clamps `LIMIT` to `row_limit`. Hard result-stream cap even if DuckDB returns more. |
| **time-of-day window** | **control plane (session mint) + gateway** | Sessions are only minted when `now()` is inside `[window_start, window_end]` (UTC). The gateway rejects sessions whose window has since elapsed on the next query. |

### Why not DuckDB views for columns and rows?

DuckDB views for column ACL are **bypassable**. An agent can reference the base table in its own view or macro (confused-deputy attack), or introspect metadata via `duckdb_columns()` to learn column names it was supposed not to see. The waddling security audit confirmed these gaps.

The gateway proxy constructs the constrained query **itself** — it parses the SQL, validates the column set against the allow-list, and forwards the rewritten query. birdshot is the table-level backstop: even if the proxy were bypassed, an ungranted table is still denied by birdshot's in-memory policy.

## The policy compiler

When you create, update, or delete an ACL rule, the **policy compiler** runs:

1. Fetches all active rules for the endpoint (where `not_before ≤ now() < expires_at` and window is open).
2. Builds a birdshot snapshot:
   ```sql
   birdshot_reset_config()
   birdshot_set_auth(issuer='https://app.getwaddling.com', audience='gw:<endpoint_id>', mode='rs256')
   birdshot_add_jwk(kid, n, e)           -- from /api/auth/jwks
   -- for each agent with active rules:
   birdshot_add_user_role('agent:<id>', 'agent_<id>')
   -- for each allow rule:
   birdshot_add_role_grant('agent_<id>', '<schema>.<table>', 'read'/'write')
   birdshot_commit_config()
   ```
3. Pushes column/row/window constraints to the gateway proxy's in-memory constraint table (POST `/gw/constraints`, internal channel).

Revocation (`birdshot_revoke`) is called independently of the compiler — it is immediate.

## Example: analyst agent with column ACL

Say `analyst` should read `sales.orders` (all columns) and `sales.customers` (only `id` and `name` — not `ssn`):

**Rules:**

| schema | table | columns | verb | effect |
|--------|-------|---------|------|--------|
| `sales` | `orders` | *(all)* | `read` | `allow` |
| `sales` | `customers` | `[id, name]` | `read` | `allow` |

**What birdshot sees:** `agent_analyst` gets `read` grant on both `sales.orders` and `sales.customers`.

**What the proxy sees:** for `(analyst, sales, customers)` the allow-list is `[id, name]`. If the agent sends `SELECT * FROM lake.sales.customers`, the proxy rewrites it to `SELECT id, name FROM lake.sales.customers` before forwarding. If the agent sends `SELECT ssn FROM lake.sales.customers`, the proxy rejects the query entirely with:

```json
{ "error": "authorization_denied", "table": "sales.customers", "reason": "column ssn not in allow-list" }
```

**What happens if the agent tries to skip the proxy?** Direct quack connections to the gateway still hit birdshot's table-level check. But column-level enforcement lives only in the proxy — this is why the proxy is a mandatory gateway layer, not optional middleware.

## Instant revoke — the denylist

`waddling_admin_revoke_agent` calls `birdshot_revoke('user', 'agent:<id>', reason, expires_us)` on the gateway. birdshot adds the principal to an in-memory denylist. The next `birdshot_authorize` call for that principal returns `deny` immediately — no policy snapshot is needed, no JWK re-verification, no restart.

The agent receives a structured error:

```json
{ "error": "authorization_denied", "reason": "agent revoked", "agent_id": "agt_xxxx" }
```

The revocation is also recorded in `waddling.audit_event` with `event='revoke'` and the actor (admin user or admin agent) that triggered it.
